1.0 — How it went

I started this because I learn best by doing. Building a small scale core and seeing where the technology began is what shows me where it leads, and that is the part of computer architecture I actually wanted to understand. The first version was single-cycle. It matched Spike, which told me the decode and the datapath were right, and that gave me a working reference to pipeline against.

Splitting it into five stages broke everything that depended on an instruction finishing before the next one started. To get the pipeline running before I had hazard hardware, I wrote a small script that pads test programs with NOPs between dependent instructions. Those padded programs are still in the regression suite, because they are the same code with the hazards removed: if forwarding ever starts producing wrong values, the padded and unpadded runs disagree and I know where to look.

Padding was never going to fix branches. NOPs behind a taken branch are harmless to the architecture, but they still retire, and Spike never executes them because RISC-V has no delay slots. The two retirement streams drift apart and lockstep falls over. Branches had to be flushed in hardware from the first pipelined version, and a taken branch costs two cycles because it resolves in EX.

The case forwarding cannot cover is a load consumed by the very next instruction, because the loaded value does not exist until the end of MEM. The hazard unit holds the PC and bubbles ID/EX for one cycle, turning it into a distance-2 dependency the existing path already handles. The cycle count backs this up: on the load-use program the arithmetic predicts 119 cycles and the core measures 120.

4.0 — Synthesis and timing on the Spartan-7

Both memories started out as arrays of flip-flops, which simulates fine and does not fit on the part. At 512 words each the design came out at 189% of the LUTs and 106% of the flops on an xc7s15, so it never placed and I had no timing number at all. Moving them into block RAM took two things and I needed both of them, neither one on its own was enough. First a synchronous read, which is what makes block mapping legal in the first place, and then the style attribute, which is what makes the tool actually choose it. Until I told it otherwise Vivado quietly picked logic for the instruction ROM and distributed RAM for the data cache.

What I actually did here was trade frequency for area. Roughly 13× the LUTs and 44× the flops came back, and about 7 MHz of Fmax went the other way. I kept the clock constraint fixed at 10 ns for every build so the rows stay comparable, thus the failing setup is telling me this is not a 100 MHz design rather than telling me it is broken. Hold is clean in every build, and hold is the one that would have meant broken at any frequency.

The other thing worth recording is that I predicted this wrong. I said block RAM would not move WNS much, and my reasoning was that the worst path at the time was branch resolution feeding back into fetch, and the branch cone does not touch memory anywhere. WNS got 1.64 ns worse instead. Removing that much area changes which path is the worst one, and I had not accounted for that.

The critical path is now the load return, start to finish in a single cycle: the block RAM's clock-to-out, then the lane mux, then sign extension, then the LOAD select, and finally the register file's write-first bypass landing in the ID/EX register. The endpoint is worth noticing, it is the bypass and not the forwarding mux. Both of them consume the same value, the bypass is just the longer of the two.

The register file went the other way and stays distributed, even though at 32 words it is the smallest memory in the design. A RAMB only has two ports total, so 2R+1W would mean duplicating the array. Its read is registered, which would push ID into two stages. And its read-during-write modes are same-port only, so the bypass mux would still be sitting there anyway, now with a latency mismatch on top of it. Capacity told me nothing useful about any of this. Port count and read latency are what actually decided it.

6.1 Pipeline and hazard handling

Forwarding is a mux per operand at the entrance to EX, sourcing from the producer one instruction ahead or two ahead, with newer-wins priority. Both operands are decided independently, and the forwarded value feeds the ALU, the target-address constructor and the store-data path from a single point, so JALR bases and store data cannot be missed.

Pipeline registers are packed structs in riscv_pkg.sv, with control bundles nested inside them, so the taper is enforced by the type system. All four flops live in top_lvl.sv, and the entire stall and flush policy is eight assignments sitting next to the flop they gate. A zeroed register struct is a NOP bubble, so reset, flush and the retire signal fall out of the type definition.

6.2 Verification method

Spike is the golden reference. Its value is independence: expected values come from software written by other people from the specification, not from the same understanding that produced the RTL. The testbench compares per retirement rather than per cycle, so pipeline fill, flushes and stalls need no special handling.

Six fields are compared at the MEM/WB boundary, ordered cheapest to interpret first, so the earliest failure is also the most localising:

pc → instruction word → rd → rd_data → mem_addr → mem_data

coverage.S retires 107. loaduse.S exists because coverage.S contains zero load-use pairs at distance two or less and therefore passes whether or not the interlock exists. It has 20 distance-1 pairs that must stall, 2 distance-2 pairs that must not, and two negative controls that check stalls do not fire when they shouldn't. loads.S came out of the same reasoning. No load test can catch a write enable that is too wide, so what it does instead is write one sub-word field into a known word and then read the whole word back.

The reset vector matches the link address because JAL, JALR and AUIPC write the PC itself into a register. A core booting at zero while Spike runs at 0x8000_0000 disagrees with the reference on all three.

6.4 What is not done yet

All 37 RV32I instructions decode and all 37 are now exercised against Spike, so instruction coverage is not what is left. The unsigned branches were the last gap and I closed them on purpose rather than by accident, because inverted and unsigned comparison is where a sign handling bug would hide, and no amount of testing on the signed forms would have found it.

The load-use detector is imprecise, and it costs me cycles rather than correctness. It compares the load's destination register against both inst[19:15] and inst[24:20] of the instruction behind it, without ever asking what format that instruction is. On an I-type consumer those second five bits are immediate bits and not a source register at all, thus a load into x5 followed by an addi that happens to have 5 in the low immediate will stall for a bubble it never needed. It is on my list because the fix is a format check the decoder is already computing.

Three cases that trap in real RV32I are deferred: misaligned data access, misaligned instruction fetch, and illegal instructions, which currently decode to a silent NOP. FENCE decodes and retires as a no-op. That happens to be architecturally correct on a single hart in-order core, but I want to be clear that it fell out that way rather than being something I set out to implement. ECALL/EBREAK and the Zicsr instructions are not implemented. Synthesis is done and measured but I have not attempted timing closure. The design places and routes with clean hold at 62 MHz on a −1 part, and I have put no effort into setup at all. Nothing has run on the board yet.
