A programmable lock, and the day simulation stopped being enough

A four-digit lock in SystemVerilog on a Basys3. It passed every simulation and then behaved erratically on the board, which is how I learned what a synchronizer chain is for.

1.0 — How it went

The idea is small on purpose. On reset the lock is programmed with a four-digit sequence entered on two buttons. Enter the same sequence and a green LED comes on for five seconds before it locks itself again. Get it wrong and it blinks red and starts over. Sixteen combinations, so nothing here is secure, but the state machine has to be exactly right.

In simulation it worked on the first serious pass. On the board it did not. Presses registered twice, or skipped, or dropped the lock into the error state for no reason I could see in the waveform, because the waveform was of a design that had never met a real button. A testbench drives inputs on clock edges. A person pressing a switch has no idea when the clock edge is.

The fix was a synchronizer chain. The first flop catches whatever the asynchronous input is doing and may go metastable. The second gives it a full cycle to settle. I ended up needing a third, because without it the settled value was being read one cycle before the debouncer's timing logic was ready for it, and the extra stage holds it long enough to be sampled correctly.

Two smaller things caught me. The board's buttons are active low, so pressed means zero and the detection logic reads inverted, which looks wrong every time you come back to it. And the one-cycle sample_valid pulse could be consumed twice by different states if the FSM was not written carefully, which turned one press into two digits.

2.0 — The three stages
button_1_sync_r1 <= button_1;          // stage 1: catch metastability
button_1_sync_r2 <= button_1_sync_r1;  // stage 2: clean output
button_1_input   <= button_1_sync_r2;  // stage 3: debouncer input

assign button_active_sync = (!button_1_sync_r2) || (!button_2_sync_r2);

Button-active detection reads stage two while the timing-critical debouncer input reads stage three. Synchronizing each button separately and combining them afterwards keeps the two buttons on independent timing paths instead of adding a stage of delay to the combined signal.

5.1 States and behaviour
PROGRAM_0-3Initial programming of the four-digit password
LOCKED_0-3Verification, one state per digit
UNLOCKEDGreen LED, five-second timeout, then relock
ERRORBlinking LED, then back to LOCKED_0. Four wrong attempts trigger a half-second blink state.

Program the password by pressing button 1, button 2, button 1, button 2, holding each for about two seconds. Unlock by repeating it. Reset returns to PROGRAM_0.

5.2 Debounce strategy

A counter increments while the button is held. When it reaches the threshold of 1,500,000 cycles at 100 MHz, which is 15 ms, and the button is then released, a sample_valid pulse fires and the input is captured. The window rejects short glitches from mechanical bounce, which typically lasts 5 to 20 ms.
