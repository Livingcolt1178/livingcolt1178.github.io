1.0 — How it went

I started this because I wanted to know what actually happens between an instruction word arriving in memory and a register being written. The first version was single-cycle. It matched Spike, which told me the decode and the datapath were right, and that gave me a working reference to pipeline against.

Splitting it into five stages broke everything that depended on an instruction finishing before the next one started. To get the pipeline running before I had hazard hardware, I wrote a small script that pads test programs with NOPs between dependent instructions. Those padded programs are still in the regression suite, because they are the same code with the hazards removed: if forwarding ever starts producing wrong values, the padded and unpadded runs disagree and I know where to look.

Padding was never going to fix branches. NOPs behind a taken branch are harmless to the architecture, but they still retire, and Spike never executes them because RISC-V has no delay slots. The two retirement streams drift apart and lockstep falls over. Branches had to be flushed in hardware from the first pipelined version.

The case forwarding cannot cover is a load consumed by the very next instruction, because the loaded value does not exist until the end of MEM. The hazard unit holds the PC and bubbles ID/EX for one cycle, turning it into a distance-2 dependency the existing path already handles. The cycle count backs this up: on the load-use program the arithmetic predicts 119 cycles and the core measures 120.

5.0 — Specifications
5.1 Pipeline and hazard handling

Forwarding is a mux per operand at the entrance to EX, sourcing from the producer one instruction ahead or two ahead, with newer-wins priority. Both operands are decided independently, and the forwarded value feeds the ALU, the target-address constructor and the store-data path from a single point, so JALR bases and store data cannot be missed.

Pipeline registers are packed structs in riscv_pkg.sv, with control bundles nested inside them, so the taper is enforced by the type system. All four flops live in top_lvl.sv, which puts the entire stall and flush policy in eight adjacent lines. A zeroed register struct is a NOP bubble, so reset, flush and the retire signal fall out of the type definition.

5.2 Verification method

Spike is the golden reference. Its value is independence: expected values come from software written by other people from the specification, not from the same understanding that produced the RTL. The testbench compares per retirement rather than per cycle, so pipeline fill, flushes and stalls need no special handling.

Six fields are compared at the MEM/WB boundary, ordered cheapest to interpret first, so the earliest failure is also the most localising:

pc → instruction word → rd → rd_data → mem_addr → mem_data

coverage.S is 108 instructions and retires 99. loaduse.S exists because coverage.S contains zero load-use pairs at distance two or less and therefore passes whether or not the interlock exists. It has 20 distance-1 pairs that must stall, 2 distance-2 pairs that must not, and two negative controls that check stalls do not fire when they shouldn't.

tohost / fromhost0x8000_13F0 / 0x8000_13F8

The reset vector matches the link address because JAL, JALR and AUIPC write the PC itself into a register. A core booting at zero while Spike runs at 0x8000_0000 disagrees with the reference on all three.

5.4 What is not done yet

bge, bltu and bgeu are implemented but no test program exercises them, so they are unverified rather than known-good. Inverted and unsigned comparisons are exactly where a sign-handling bug would hide.

Three cases that trap in real RV32I are deferred: misaligned data access, misaligned instruction fetch, and illegal instructions, which currently decode to a silent NOP. FENCE, ECALL/EBREAK and the Zicsr instructions are not implemented. Synthesis and timing closure are not done.
